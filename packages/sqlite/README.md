# @symbiote-native/sqlite

A wrapper package for [SymbioteNative](../../README.md) that makes
[`expo-sqlite`](https://github.com/expo/expo/tree/main/packages/expo-sqlite) usable from every
adapter — `Database`, `Statement`, `Session` (transactions and changesets), a Bun-style SQL
tagged-template helper, and a SQLite-backed key-value store. Built the same way as
[`@symbiote-native/secure-store`](../secure-store): an `expo-modules-core`-based wrapper (see the
`symbiote-expo-native-module` project skill for the full mechanism — why `expo-modules-core` is
depended on directly and never the `expo` meta-package, why the upstream JS is hand-ported into
`core/` rather than imported, and how autolinking picks up the native module).

Every adapter — React, Vue, Svelte, Solid, Angular — ships its own idiomatic `<SQLiteProvider>` /
`useSQLiteContext` equivalent (see "Provider / context" below), reachable from its own subpath.
Each subpath re-exports the full `src/core/` barrel too, so importing from `@symbiote-native/sqlite/react`
(etc.) is a strict superset of importing from the package root.

expo-sqlite's native classes — `NativeDatabase`, `NativeStatement`, `NativeSession` — are **plain
constructors** exposed as properties on the required native module (`new
ExpoSQLite.NativeDatabase(...)`), unlike `@symbiote-native/audio`'s JSI-backed `SharedObject`
subclasses. There is nothing to subclass here: this package's `SQLiteDatabase` /
`SQLiteStatement` / `SQLiteSession` wrapper classes hold a native instance and forward to it,
exactly like upstream's own.

## Install

**New app:**

```bash
npx @symbiote-native/cli new my-app --sqlite
```

**Existing SymbioteNative app:**

```bash
npx @symbiote-native/cli add --sqlite
```

Either way: installs `@symbiote-native/sqlite` and wires the native autolinking automatically — see
[`@symbiote-native/cli`](../cli).

<details>
<summary>Manual install (no CLI — installing and wiring native autolinking by hand)</summary>

```bash
npm install @symbiote-native/sqlite
```

`expo-sqlite` and `expo-modules-core` come along as regular dependencies, pinned to exact
versions — never install either yourself, and never add the `expo` meta-package to your project
(it bundles its own Metro/Babel pipeline, which conflicts with this project's own). `await-lock`
is a real runtime dependency of the kv-store (see "Shape" below), not a native-only placeholder.

### Required one-time step: native autolinking wiring

Same one-time step as every other `expo-modules-core` package this project ships — see
[`@symbiote-native/local-auth`'s README](../local-auth/README.md#required-one-time-step-native-autolinking-wiring)
and the `symbiote-expo-native-module` project skill. Nothing package-specific: iOS autolinks the
`Expo` pod automatically; Android's Gradle project + native-module map entry is generated by
[`@symbiote-native/expo-modules-link`](../expo-modules-link)'s aggregator from this package's
`native-link.json` on every install.

expo-sqlite compiles its own vendored SQLite amalgamation from source per platform (it does not
link the OS's system `libsqlite3`) — expect `pod install`/the first Android build touching this
package to be noticeably heavier than a package that only links a prebuilt framework. That is
expected, not a broken build.

</details>

## Shape

```
src/core/   native-database.ts / native-statement.ts / native-session.ts — the ambient
            `declare class` surface expo-sqlite's native module exposes, ported type-only.
            native-module.ts — resolves `ExpoSQLite` via expo-modules-core's requireNativeModule.
            sqlite-database.ts / sqlite-statement.ts / sqlite-session.ts — the real wrapper
            classes, holding a native instance and forwarding to it.
            sqlite-tagged-query.ts — the `db.sql`...`` tagged-template helper.
            storage.ts — SQLiteStorage, the SQLite-backed key-value store (its own subpath, see
            below). query-utils.ts / path-utils.ts / param-utils.ts — framework/native-free
            helpers (SQL-shape parsing, database-path joining, bind-param normalization).
```

`@symbiote-native/sqlite/kv-store` is a **separate subpath**, not re-exported from the package
root — `SQLiteStorage`/`AsyncStorage`/`Storage` pull in `await-lock` and open their own database
lazily on first use; an app that only wants `Database`/`Statement`/`sql` should not pay for that
by importing it transitively.

## Use it

```ts
import { openDatabaseAsync } from '@symbiote-native/sqlite';

const db = await openDatabaseAsync('app.db');
await db.execAsync('CREATE TABLE IF NOT EXISTS todos (id INTEGER PRIMARY KEY, title TEXT)');
await db.runAsync('INSERT INTO todos (title) VALUES (?)', 'Buy milk');
const todos = await db.getAllAsync<{ id: number; title: string }>('SELECT * FROM todos');
```

The SQL tagged-template helper (Bun-style, automatically parameterized):

```ts
const users = await db.sql<User>`SELECT * FROM users WHERE age > ${21}`;
const rows = await db.sql`SELECT name, age FROM users`.values(); // [["Alice", 30], ...]
const user = await db.sql<User>`SELECT * FROM users WHERE id = ${id}`.first();
for await (const user of db.sql<User>`SELECT * FROM users`.each()) {
  /* ... */
}
```

Transactions:

```ts
await db.withTransactionAsync(async () => {
  await db.runAsync('UPDATE accounts SET balance = balance - ? WHERE id = ?', 100, from);
  await db.runAsync('UPDATE accounts SET balance = balance + ? WHERE id = ?', 100, to);
}); // rolls back and re-throws if the task throws
```

The key-value store, from its own subpath:

```ts
import { AsyncStorage } from '@symbiote-native/sqlite/kv-store';

await AsyncStorage.setItem('token', 'secret');
const token = await AsyncStorage.getItem('token'); // string | null
```

### `onInit` — a deliberate deviation from upstream

Upstream only exposes `onInit` as a `SQLiteProviderProps` field, called by its React
`<SQLiteProvider>` after opening, before rendering children. Here `onInit` is exposed directly on
`openDatabaseAsync`/`openDatabaseSync` instead — called once, right after the native handle opens,
before the function returns:

```ts
const db = await openDatabaseAsync('app.db', {
  onInit: async db => {
    await db.execAsync('CREATE TABLE IF NOT EXISTS todos (id INTEGER PRIMARY KEY, title TEXT)');
  },
});
```

This gives an adapter with no view-tree context — a plain module-scope call, or Angular's
`SqliteService` — a "run this once right after open" hook without needing a Provider to exist
first. Every Provider above forwards its own `onInit` prop straight into `openDatabaseAsync`
rather than calling it a second time. `openDatabaseSync` rejects (throws) if its `onInit` returns
a `Promise`, rather than silently racing it.

## Provider / context (per adapter)

Each adapter's Provider opens the database once (closing and reopening if its config props
change), renders nothing until it resolves, and hands the open `SQLiteDatabase` to descendants.
On failure it calls `onError` if given, else the failure propagates through whatever error
channel is idiomatic to that framework (a rethrow, an unhandled rejection, a resource-read
throw — see each adapter's own source comment for the exact mechanism). `onInit` is forwarded to
`openDatabaseAsync` (which already runs it — see below), not called a second time.

**React** (`@symbiote-native/sqlite/react`):

```tsx
import { SQLiteProvider, useSQLiteContext } from '@symbiote-native/sqlite/react';

<SQLiteProvider databaseName="app.db" onInit={migrate}>
  <Main />
</SQLiteProvider>;

function Main() {
  const db = useSQLiteContext();
  // ...
}
```

`useSuspense` is also supported (React's own primitive — `<Suspense>` shows its fallback instead
of the Provider rendering `null`).

**Vue** (`@symbiote-native/sqlite/vue`):

```ts
import { SQLiteProvider, useSQLiteContext } from '@symbiote-native/sqlite/vue';
// <SQLiteProvider database-name="app.db"><Main /></SQLiteProvider> in a template
// useSQLiteContext() inside a descendant's setup()
```

**Svelte** (`@symbiote-native/sqlite/svelte`):

```svelte
<script>
  import { SQLiteProvider, useSQLiteContext } from '@symbiote-native/sqlite/svelte';
</script>

<SQLiteProvider databaseName="app.db">
  <Main />
</SQLiteProvider>
```

**Solid** (`@symbiote-native/sqlite/solid`):

```tsx
import { SQLiteProvider, useSQLiteContext } from '@symbiote-native/sqlite/solid';

<SQLiteProvider databaseName="app.db">
  <Main />
</SQLiteProvider>;
```

**Angular** (`@symbiote-native/sqlite/angular`) — DI, not a template Provider (this project's
established Angular idiom, see `@symbiote-native/navigation`'s own context service):

```ts
import { SqliteService, provideSqliteDatabase } from '@symbiote-native/sqlite/angular';

// app config / module providers:
provideSqliteDatabase({ databaseName: 'app.db', onInit: migrate });

// any component/service:
constructor(private readonly sqlite: SqliteService) {}
// this.sqlite.database() — an Angular `resource()`-backed signal
```

None of the five ports upstream's `assetSource` option (see "Deliberately out of scope" below).
React's `useSuspense` has no equivalent on the other four — Vue/Solid have their own native
`<Suspense>`/`createResource` primitives an app can compose around the Provider itself if wanted;
Svelte and Angular have none, and none of the four non-React Providers builds a second opt-in
code path for it (a deliberate framework-idiom divergence, not a gap — each adapter's own source
file says so at the top).

## Error handling

Native errors surface as a plain thrown `Error`/rejected `Promise` — upstream's ~12 native
`Exception`/`GenericException` JS classes are not ported, same convention as every other
module-only package this project ships. Trigger conditions, from the vendored native source
(`.vendors/expo` @ `origin/sdk-57`, `packages/expo-sqlite/{android,ios}`):

| Message contains                                   | Triggered by                                                                     |
| --------------------------------------------------- | --------------------------------------------------------------------------------- |
| `Could not open database` / invalid path             | The native `sqlite3_open` call for the resolved path failed.                     |
| `Database '<name>' not found`                        | Deleting a database that was never opened / does not exist on disk.              |
| `Unable to delete database '<name>' that is currently open` | `deleteDatabaseAsync`/`Sync` on a database with a still-open connection. Close it first. |
| `Unable to delete the database file for '<name>' database` | The file delete itself failed after the open-connection check passed.            |
| `Access to closed resource`                          | Any call on a `SQLiteDatabase`/`SQLiteStatement`/`SQLiteSession` after `close*`/`finalize*`. |
| `Invalid bind parameter`                              | A bind value's type SQLite's C binding layer cannot marshal.                     |
| `Invalid arguments: ...`                              | A malformed call into the native layer (wrong argument shape).                   |
| `ERR_INTERNAL_SQLITE_ERROR` (code) / raw SQLite message | SQLite itself rejected the statement — malformed SQL, constraint violation, etc. |
| `Unsupported operations`                              | An operation the current build (e.g. a non-libSQL build calling `syncLibSQL()`) does not support. |

## Deliberately out of scope

- **The `assetSource` bundled-database-file option**
  (`openDatabaseAsync(name, options, { assetSource })`) — needs `expo-asset`'s
  `Asset.fromModule`, which this project deliberately does not depend on (same exclusion class as
  `@symbiote-native/audio`'s `Asset`-instance form of `AudioSource` — see that package's README).
  A file-copy-based alternative through [`@symbiote-native/file-system`](../file-system)'s
  `File`/`Directory` API is possible but not wired here.
- **The `expo-sqlite/plugin` config plugin** (libSQL / `sqlite-vec` extension bundling config) —
  manual per-app native configuration, same convention as
  [`@symbiote-native/notifications`'s README](../notifications/README.md) documenting manual
  Firebase/entitlement setup. `bundledExtensions`/`loadExtensionAsync`/`loadExtensionSync` are
  still exported and work against whatever extensions your app's own native build actually
  bundles — they just require you to wire that bundling yourself.
- **`importAssetDatabaseAsync`** — copies a bundled asset database into place at first launch;
  layers on top of the `assetSource` exclusion above, so it is out of scope for the same reason.
- **Web-only surfaces** (`ExpoSQLite.web.ts`, `WebStorage.ts`) — this project targets iOS +
  Android only.
- **expo-sqlite's own DevTools-browser-extension wiring** (`SQLiteDevToolsClient.ts`) — this
  project has no equivalent of Expo's DevTools plugin.

## Test it

```bash
pnpm vitest run packages/sqlite
```

The core tests fake the native module in place of `requireNativeModule`'s runtime resolution —
`ExpoSQLite` only exists on a device, so a headless run would otherwise throw at import. Unlike
this project's other `expo-modules-core` wrappers, the fake here (`src/core/native-fakes.ts`)
wraps a **real [`better-sqlite3`](https://github.com/WiseLibs/better-sqlite3) database** rather
than a hand-rolled stub, so tests exercise genuine SQL behavior — real transactions, real
constraint errors, real column shapes — not a guess at what SQLite would do. `better-sqlite3` is
a devDependency only; it is never shipped to a consumer and is excluded from the published
tarball alongside the fakes themselves.

Real database-file persistence across app restarts, native extension loading, and libSQL sync can
only be verified on a device or emulator.
