# @symbiote-native/sms

Open the system SMS composer with recipients, a message and optionally an attachment already
filled in. One API for every [SymbioteNative](../../README.md) adapter (React, Vue, Svelte, Solid
and Angular).

It wraps [`expo-sms`](https://github.com/expo/expo/tree/main/packages/expo-sms) the same way
[`@symbiote-native/secure-store`](../secure-store) wraps its upstream: `expo-modules-core` is a
direct dependency, never the `expo` meta-package, and the upstream JS is hand-ported into `core/`.
The mechanics live in the `symbiote-expo-native-module` project skill.

Nothing is ever sent on the user's behalf. Both platforms open their own composer with the draft
filled in; the user presses send, edits, or discards it.

## Install

**New app:**

```bash
npx @symbiote-native/cli new my-app --sms
```

**Existing SymbioteNative app:**

```bash
npx @symbiote-native/cli add --sms
```

Either way: installs `@symbiote-native/sms` and wires the native autolinking automatically - see
[`@symbiote-native/cli`](../cli).

### Required one-time step: native autolinking wiring

Unlike a plain RN native module, `expo-sms`'s native code is discovered by
`expo-modules-autolinking` - this needs wiring into the native host app **once**, covering this
package and every other `expo-modules-core` package with zero further changes:

| Platform | Touches                                                                               |
| -------- | ------------------------------------------------------------------------------------- |
| iOS      | `ios/Podfile` - add `use_expo_modules!`                                               |
| iOS      | `AppDelegate.swift` - Expo's runtime-bootstrap hook                                   |
| Android  | `settings.gradle` / `app/build.gradle` - resolve and include the Expo Gradle projects |
| Android  | `MainApplication.kt` - Expo's bootstrap hook, plus a native-module name map           |

Full mechanics live in the `symbiote-expo-native-module` skill. The per-package half of that
table - the Gradle dependency and the module map entry - is generated by
[`@symbiote-native/expo-modules-link`](../expo-modules-link) from this package's
`native-link.json` on every install.

### No permissions, no manifest edits, no config plugin

This is the least invasive of the Expo wrappers here:

- **No runtime permission on either platform.** Opening the composer is an intent
  (`ACTION_SENDTO`/`ACTION_SEND`) on Android and an `MFMessageComposeViewController` on iOS -
  the user's own app does the sending, so neither platform asks for one. `expo-sms` requests no
  permission anywhere in its native code, and reading the _outcome_ of a sent message on Android
  would need `READ_SMS`, which is exactly why it doesn't try (see the `unknown` result below).
- **No `Info.plist` usage-description key.**
- **No manifest edit.** `expo-sms` ships its own `<queries>` block declaring the `SEND`/`SENDTO`
  intents it resolves, needed on Android 11+ package-visibility rules; it merges into your app
  automatically once the Gradle project is included.
- **No config plugin.** Upstream ships none at all, so there is nothing else to apply.

## Shape

```
src/core/                 the whole API: sendSMSAsync + isAvailableAsync. native-module.ts
                          resolves ExpoSMS through expo-modules-core's requireNativeModule.
src/angular/              @symbiote-native/sms/angular
```

`./react`, `./vue`, `./svelte`, and `./solid` are `exports`-map aliases straight onto `src/core/` -
no physical per-framework file. Both exports are stateless free functions - `sendSMSAsync` resolves
once the composer closes and holds nothing afterwards, and there is no event stream - so there is
nothing for a hook, composable, or service to wrap, the same reason
[`@symbiote-native/secure-store`](../secure-store) does the same. `./angular` stays a physical
file/subpath since Angular ships through a separate `ngc`/AOT build (`build-ngc/`). Import from
`@symbiote-native/sms` directly if you don't care which adapter you're on; the per-adapter
subpaths exist so every wrapper package has the same import surface.

## Use it

```ts
import { isAvailableAsync, sendSMSAsync } from '@symbiote-native/sms';

if (await isAvailableAsync()) {
  const { result } = await sendSMSAsync(
    ['0123456789', '9876543210'],
    'Running late, sorry!',
  );
  // 'sent' | 'cancelled' on iOS; always 'unknown' on Android
}
```

A single recipient may be passed as a bare string - it is normalised into an array before the
native call:

```ts
await sendSMSAsync('0123456789', 'Running late, sorry!');
```

With an attachment:

```ts
await sendSMSAsync('0123456789', 'Here is the receipt', {
  attachments: {
    uri: 'content://media/external/images/media/1',
    mimeType: 'image/png',
    filename: 'receipt.png',
  },
});
```

The `uri` has to be a **content** URI - the composer runs in another app's process, and a plain
file path is not readable from there.

## API

| Export             | Signature                                                 | Notes                                                                                                       |
| ------------------ | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `isAvailableAsync` | `() => Promise<boolean>`                                  | `false` on the iOS simulator, which has no Messages app, and on Android devices without telephony hardware. |
| `sendSMSAsync`     | `(addresses, message, options?) => Promise<ISmsResponse>` | Opens the composer. Resolves when it closes. Throws if the device has no messaging app.                     |

`ISmsOptions`: `attachments` - one `ISmsAttachment` or a list of them.
`ISmsAttachment`: `uri` (content URI), `mimeType`, `filename`.
`ISmsResponse`: `{ result: 'sent' | 'cancelled' | 'unknown' }`.

## Notes

- **Check `isAvailableAsync()` first.** It resolves `false` on devices that cannot send text, such as
  an iOS simulator or a tablet without telephony, and `sendSMSAsync` rejects there.
- **Android always resolves `unknown`.** The only way to learn whether a message actually left
  the device is to query the SMS database, which needs the `READ_SMS` permission Google restricts
  to default-SMS-app publishers. Treat `unknown` as "the composer closed", not as a failure.
- **Android carries one attachment.** Its composer intent has a single `EXTRA_STREAM` slot, so
  anything past the first is dropped before the native call rather than silently ignored deeper
  down. iOS attaches all of them.
- **`sendSMSAsync` can reject.** Android throws when no messaging application is installed; iOS
  throws when the device cannot send text at all, or when a composer is already open.

## Common questions

- **`isAvailableAsync()` is `false` on the iOS Simulator.** Expected: it cannot send text.
- **Android: "No messaging application available".** No installed app handled the intent; the
  package ships the Android 11 `<queries>` entries, so check a messaging app exists.
- **Silent send?** No: the user presses send in the system composer.
- **Result is not `sent` on Android.** It always resolves `unknown`.
- **One attachment arrives on Android.** The composer takes one; iOS attaches all.

Sources: [Expo docs: SMS](https://docs.expo.dev/versions/latest/sdk/sms/),
[expo/expo#13277](https://github.com/expo/expo/issues/13277),
[expo/expo#2384](https://github.com/expo/expo/issues/2384).

## Test it

```bash
pnpm vitest run packages/sms
```

The core tests fake the native module in place of `requireNativeModule`'s runtime resolution -
`ExpoSMS` only exists on a device, so a headless run would otherwise throw at import. The
composer itself, and the `sent`/`cancelled` distinction, can only be verified on a device.
