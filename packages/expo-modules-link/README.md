# @symbiote-native/expo-modules-link

Native-module registration for apps using SymbioteNative's expo-modules-core wrapper packages
(`@symbiote-native/sensors`, `@symbiote-native/local-auth`, `@symbiote-native/haptics`, ...).

## Why this exists

Every `expo-modules-core`-based package (see the `symbiote-expo-native-module` skill) needs
two Android registration steps that RN's own autolinking can't reach, because there's no
`expo` aggregator package generating them: an `implementation project(':expo-<pkg>')` line in
the app's `android/app/build.gradle`, and a `ModulesProvider` map entry (import + class-to-name
mapping) in its `MainApplication.kt`. Left as a manual step, a missed entry compiles cleanly
and only fails at **runtime** with `Cannot find native module '<Name>'` - this has bitten the
project more than once.

## Setup (once per app)

```json
{
  "dependencies": {
    "@symbiote-native/expo-modules-link": "^0.2.0"
  },
  "scripts": {
    "postinstall": "symbiote-expo-link"
  }
}
```

That's the whole integration. Every wrapper package you install afterwards is picked up
automatically on the next install - no per-package step. You can also run it by hand at any
time with `npx symbiote-expo-link`.

## What a wrapper package ships

Next to its `package.json`, a `native-link.json` manifest declaring what it needs registered.
It has no `postinstall` of its own - the manifest is passive data the aggregator reads.

```json
{
  "android": {
    "gradleProjectName": "expo-local-authentication",
    "modules": [
      {
        "importPath": "expo.modules.localauthentication.LocalAuthenticationModule",
        "className": "LocalAuthenticationModule",
        "nativeName": "ExpoLocalAuthentication"
      }
    ]
  }
}
```

`nativeName` must match that module's own `definition() { Name("...") }` string exactly -
that's the key `requireNativeModule(...)` resolves by on the JS side.

## How it works

One process, one pass: scan the app's `node_modules` for every installed package shipping a
`native-link.json`, sort them by package name, and regenerate the registration blocks from
that list. Each block is a region delimited by a marker pair, and the generator owns
everything between them:

```gradle
    // SYMBIOTE-EXPO-LINK:BEGIN DEPENDENCIES (generated by symbiote-expo-link - do not edit, regenerated on every install)
    implementation project(':expo-application')
    implementation project(':expo-battery')
    // SYMBIOTE-EXPO-LINK:END DEPENDENCIES
```

Everything outside the markers is yours and is never touched. Files are written atomically
(temp file + rename), so an interrupted install can't leave a half-written `build.gradle`.

If the app isn't a React Native project (no `android/app/build.gradle`, no `ios/*/Info.plist`),
or an anchor is missing, it says so and exits cleanly - linking never fails an `npm install`.

## Why an aggregator, and not a per-package postinstall

The previous design had every wrapper package's own `postinstall` append its own line. Package
managers run sibling lifecycle scripts concurrently, so that meant N independent OS processes
doing read-modify-write on one shared file - two of them could read the same version before
either wrote back, and the later write silently dropped the earlier one's registration.

Fixing that needs cross-process mutual exclusion, and a correct file lock is not reachable from
plain `fs`: there is no compare-and-unlink and no `flock`, so "decide the holder is dead" and
"act on it" stay two separate steps with a window in between. Successive attempts narrowed that
window but never closed it - the last measured about one lost registration per hundred installs.

Removing the concurrency removed the problem outright, and took three long-standing annoyances
with it. Entries are sorted now, so committed native files stop churning with a different order
on every machine. Uninstall works, because a region is rewritten from the current truth while an
append-only patcher could only ever grow the list. And there are no `.lock` files left to leak,
gitignore, or clean up after a Ctrl-C.

This is also how Expo itself does it: `expo-modules-autolinking` scans the installed tree from
a single process rather than having each package register itself.

## iOS Info.plist permission strings

A package that needs a usage-description string (e.g. `NSFaceIDUsageDescription` for
`local-auth`, `NSMotionUsageDescription` for `sensors`, `NSUserTrackingUsageDescription` for
`tracking-transparency`) declares it in `native-link.json` under `ios.infoPlistKeys`. The value
is a **generic, app-agnostic default** - this tool has no config file to read a custom string
from, so it can never know your app's name or tone (never copy an example app's own demo
wording into a package's shipped default - this bit us once during development).

Unlike the Android blocks, Info.plist gets **no generated region**. Xcode rewrites this file
through its own plist serializer whenever target settings change, and that serializer drops XML
comments - losing an END marker would make the next run insert a second block and produce
duplicate keys, an invalid plist. So iOS stays additive: the presence of `<key>NAME</key>` is
itself the idempotency check.

That makes overriding a description free:

- Add the key to your `Info.plist` with your own wording **before** installing the package →
  the default never gets inserted at all.
- Edit the generated string **any time after** → the key exists, so every future run leaves it
  alone permanently.

When your wording and the package's default disagree, the run prints a one-line notice naming
both. It keeps your file as-is - the point is that drift is visible, not that it's corrected.

## Scope

Android registration (`build.gradle` + `MainApplication.kt`) plus iOS Info.plist permission
strings. iOS's own autolinking (`use_expo_modules!(exclude: [...])` in the app's Podfile)
already auto-discovers every installed expo-modules-core package with zero per-package Podfile
edits once wired - see the `symbiote-expo-native-module` skill. The one-time per-app native
bootstrap (Podfile monkey-patch, `SymbioteExpoModulesFactory`, bridging header) is still a
manual, one-time step per app - this package only automates the *recurring* per-package
registration that repeats on every new native module.
