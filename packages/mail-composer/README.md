# @symbiote-native/mail-composer

A wrapper package for [SymbioteNative](../../README.md) that makes
[`expo-mail-composer`](https://github.com/expo/expo/tree/main/packages/expo-mail-composer) —
opening the system mail composer prefilled with recipients, subject, body, and attachments —
usable from **every** adapter, React, Vue, Svelte, Solid, and Angular, not just React. Built the
same way as [`@symbiote-native/sms`](../sms): an `expo-modules-core`-based wrapper (see the
`symbiote-expo-native-module` project skill for the full mechanism — why `expo-modules-core` is
depended on directly and never the `expo` meta-package, why the upstream JS is hand-ported into
`core/` rather than imported, and how autolinking picks up the native module).

Nothing is ever sent on the user's behalf. Both platforms open their own composer with the draft
filled in; the user presses send, edits, or discards it.

## Install

**New app:**

```bash
npx @symbiote-native/cli new my-app --mail-composer
```

**Existing SymbioteNative app:**

```bash
npx @symbiote-native/cli add --mail-composer
```

Either way: installs `@symbiote-native/mail-composer` and wires the native autolinking
automatically — see [`@symbiote-native/cli`](../cli).

<details>
<summary>Manual install (no CLI — installing and wiring native autolinking by hand)</summary>

```bash
npm install @symbiote-native/mail-composer
```

`expo-mail-composer` and `expo-modules-core` come along as regular, pinned dependencies — never
install either yourself, and never add the `expo` meta-package to this project (it bundles its
own Metro/Babel pipeline that conflicts with this project's own).

### Required one-time step: native autolinking wiring

Unlike a plain RN native module, `expo-mail-composer`'s native code is discovered by
`expo-modules-autolinking` — this needs wiring into the native host app **once**, covering this
package and every other `expo-modules-core` package with zero further changes:

| Platform | Touches                                                                               |
| -------- | ------------------------------------------------------------------------------------- |
| iOS      | `ios/Podfile` — add `use_expo_modules!`                                               |
| iOS      | `AppDelegate.swift` — Expo's runtime-bootstrap hook                                   |
| Android  | `settings.gradle` / `app/build.gradle` — resolve and include the Expo Gradle projects |
| Android  | `MainApplication.kt` — Expo's bootstrap hook, plus a native-module name map           |

Full mechanics live in the `symbiote-expo-native-module` skill. The per-package half of that
table — the Gradle dependency and the module map entry — is generated by
[`@symbiote-native/expo-modules-link`](../expo-modules-link) from this package's
`native-link.json` on every install.

### One Info.plist array key, no permissions, no config plugin

- **No runtime permission on either platform.** Composing is a `MFMailComposeViewController` on
  iOS and an `ACTION_SENDTO` chooser on Android — the user's own Mail app sends it.
- **`LSApplicationQueriesSchemes` (iOS only).** `getClients()` checks each candidate mail app's
  URL scheme with `canOpenURL`, which iOS 9+ silently refuses for an undeclared scheme — so
  `native-link.json` carries the same 22-scheme list upstream's config plugin writes, generated
  into your `Info.plist` automatically (merges additively with any other package's own entries).
- **No manifest edit.** `expo-mail-composer` ships its own `<queries>` block for Android 11+
  package-visibility rules; it merges in automatically once the Gradle project is included.
- **No config plugin beyond the Info.plist key above.**

## Shape

```
src/core/                 the whole API: composeAsync + isAvailableAsync + getClients.
                          native-module.ts resolves ExpoMailComposer through
                          expo-modules-core's requireNativeModule.
src/angular/              @symbiote-native/mail-composer/angular
```

`./react`, `./vue`, `./svelte`, and `./solid` are `exports`-map aliases straight onto `src/core/` —
no physical per-framework file. All three exports are stateless free functions with no event
stream, so there is nothing for a hook, composable, or service to wrap — the same reason
[`@symbiote-native/sms`](../sms) does the same. `./angular` stays a physical file/subpath since
Angular ships through a separate `ngc`/AOT build (`build-ngc/`). Import from
`@symbiote-native/mail-composer` directly if you don't care which adapter you're on; the
per-adapter subpaths exist so every wrapper package has the same import surface.

## Use it

```ts
import { composeAsync, isAvailableAsync } from '@symbiote-native/mail-composer';

if (await isAvailableAsync()) {
  const { status } = await composeAsync({
    recipients: ['support@example.com'],
    subject: 'Order #1234',
    body: 'Hi, I have a question about my order.',
  });
  // 'sent' | 'saved' | 'cancelled' on iOS; always 'sent' on Android
}
```

Listing installed mail clients (iOS reports each one's URL scheme; Android its package name):

```ts
import { getClients } from '@symbiote-native/mail-composer';

const clients = getClients();
// [{ label: 'Gmail', url: 'googlegmail://' }, ...] on iOS
// [{ label: 'Gmail', packageName: 'com.google.android.gm' }, ...] on Android
```

With an attachment:

```ts
await composeAsync({
  recipients: ['support@example.com'],
  attachments: ['file:///path/to/receipt.pdf'],
});
```

## API

| Export             | Signature                                             | Notes                                                              |
| ------------------ | ------------------------------------------------------ | ------------------------------------------------------------------- |
| `isAvailableAsync` | `() => Promise<boolean>`                                | `false` on iOS under an MDM profile blocking outgoing mail.          |
| `composeAsync`     | `(options: IMailComposerOptions) => Promise<IMailComposerResult>` | Opens the composer. Resolves when it closes.               |
| `getClients`       | `() => IMailClient[]`                                    | Synchronous — no native round-trip needed.                        |

`IMailComposerOptions`: `recipients` / `ccRecipients` / `bccRecipients` (string arrays), `subject`,
`body`, `isHtml`, `attachments` (app-internal file URIs).
`IMailComposerResult`: `{ status: 'undetermined' | 'sent' | 'saved' | 'cancelled' }`.
`IMailClient`: `label`, plus `url` (iOS) or `packageName` (Android).

## Notes

- **Android always resolves `sent`.** It has no way to read the composer's real outcome back —
  upstream reports the same fixed status there.
- **iOS needs a signed-in Mail app.** `isAvailableAsync`/`composeAsync` fail without one —
  the same check `MFMailComposeViewController.canSendMail()` makes natively.

## Test it

```bash
pnpm vitest run packages/mail-composer
```

The core tests fake the native module in place of `requireNativeModule`'s runtime resolution —
`ExpoMailComposer` only exists on a device, so a headless run would otherwise throw at import. The
composer itself, and the `sent`/`saved`/`cancelled` distinction, can only be verified on a device.
